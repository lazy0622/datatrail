# 粒度守卫：合成扰动、合法对照与模型修复挑战 v1

日期：2026-11-11。基于 DataTrail `fbefb0d`；**本轮没有改动守卫或其他核心代码**。
这是小型合成机制实验和同作者新探针，不是公开 Olist 自然任务成功率，也不是独立留出集。

## 结论

- 支付/商品明细拆分保持业务总额不变，但会改变错误原始关联查询的结果；现有守卫能要求复核指定的原始金额 SUM 模式。
- 两个明确注入错误 SQL 的真实模型场景中，C 组均在执行前拒绝候选，模型随后改写得到正确最终答案；B 组执行过错误候选，但也自行复核改写并得到正确答案。因此**没有观察到额外最终准确率收益**。
- 两个不提供 SQL 的新自然语言探针，B/C 均正确，C 的守卫均未触发。这两题由同一评测作者预先编写，不是独立盲测。
- 发现复核成本和漏检：限定首笔支付的正确样本也被复核；明确分摊合同的正确样本仍被复核；未限定金额列名及只预聚合商品后再关联原始支付的错误查询可能漏过。**不将 gate 返回 None 解释为 SQL 已被证明安全。**

## 1. 合成数据与独立 oracle

三个订单：o1/o2 已交付且在 2018 年 7 月下单；o3 取消，必须排除。
o1 含两条同价商品（10、10）及运费（1、2），支付总额 25；
o2 商品 30、运费 3、支付 33。业务范围限定同时有商品与支付记录的已交付订单。

构造四个临时 SQLite 数据库，结束后清理，不改原 Olist 数据：

1. base。
2. split_payments：o1 支付 25 拆为 10+15，总支付金额不变。
3. split_items：o2 商品 30/运费 3 拆为商品 12+18/运费 1+2，总商品/运费不变。
4. split_both：同时应用上述两种拆分。

每个库先分别读取订单、商品、支付表，在独立 Python 中按订单汇总，再与参考 SQL 比较。
四个库均得到商品 **50**、运费 **6**、支付 **58**、订单 **2**；参考 SQL 使用 EXISTS 或完整预聚合。
这些样本使用整数金额，避免浮点舍入掩盖这里的关联问题。

| 候选 SQL | base | 拆支付 | 拆商品 | 同时拆分 | 守卫 |
| --- | ---: | ---: | ---: | ---: | --- |
| R01 原始关联 SUM(i.price)，期望 50 | 50 | 70 | 50 | 70 | 四库均复核 |
| R02 原始关联 SUM(p.payment_value)，期望 58 | 83 | 83 | 116 | 116 | 四库均复核 |
| R03 原始关联 SUM(i.price+i.freight_value)，期望 56 | 56 | 79 | 56 | 79 | 四库均复核 |
| R04 SUM(DISTINCT i.price)，期望 50 | 40 | 40 | 40 | 40 | 四库均复核 |
| U01 未限定列名 SUM(price)，期望 50 | 50 | 70 | 50 | 70 | 四库均未复核 |
| U02 只预聚合商品再关联原始支付，期望 50 | 50 | 70 | 50 | 70 | 四库均未复核 |

R01/R03 在 base 上恰好正确，扰动后暴露重复累计。R04 显示按金额 DISTINCT 会丢失不同商品的相同金额。
四库是相关的扰动样本，不应当作四个独立业务任务。

## 2. 合法控制与复核成本

共 13 个 SQL 候选 × 4 场景 = 52 条观察，完整记录见 [OFFLINE_RESULTS.json](OFFLINE_RESULTS.json)。

- L01–L05 为 EXISTS、支付 EXISTS、完整预聚合、COUNT DISTINCT、完整预聚合含运费查询；共 20 条观察，独立 oracle 均一致，未被复核。
- L06 在样本中用 `payment_sequential=1` 保留每订单恰好一条支付，商品金额四库均为 50；4 条观察均被复核。
- L07 明确声明按支付金额比例分摊商品金额再汇总，四库均为 50；4 条观察均被复核。守卫反馈要求先询问分摊口径，未利用本实验已明确的分摊合同。
- U01/U02 各在拆支付/同时拆分时数值错误且未复核，共 4 条已知错误漏过。它们不计入“合法控制未误拦”。

普通合法控制共 24 条观察中 4 条被复核；另有 4 条明确分摊观察被复核。这里只报告给定样本中的复核成本，不推断真实总体误拦率。
合法控制在四个库正确，也不能证明它们对任意数据库都语义正确。守卫本身的输出是保守复核请求，不等于一项 SQL 错误判决。

### 沿用指标的限制

原始 JSON 保留既有 grader 的 `last_sql_correct`：它实际只比较“最后一条查询的原样结果”与“最终答案目标”。
本轮模型经常在正确聚合后追加明细诊断，或返回额外检查列，故该字段为 false **不表示 SQL 错误或最终回答错误**。
本轮以 `final_correct`、查询轨迹与 oracle 为准，不用最后一条查询形状给多步流程判错。

## 5. 目前能够陈述的个人贡献

可以说：实现了限定 SQL 模式的执行前复核；在合成扰动和两项注入修复流程中验证触发与模型改写，同时记录了合法查询复核成本和漏检范围。
暂不能说：该守卫已提高真实 Olist 自然任务准确率、消除任意关联错误，或带来稳定的性能/成本收益。

后续若继续投入，先评估真实用户任务中风险模式的发生率和复核成本，再决定完善规则还是将其保留为可选诊断工具。
